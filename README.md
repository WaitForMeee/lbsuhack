# TalentHub API

HTTP API для отдельно развёрнутого фронтенда TalentHub: ученики, родители, школы, компании и академии, модератор. Python 3.13, FastAPI, синхронный SQLAlchemy, PostgreSQL, Alembic, Argon2 и Bearer JWT.

## Подготовка

Нужны Python 3.13, `uv` и PostgreSQL. Миграции автоматически создают отдельную схему `talenthub_v2`; можно использовать существующую БД, сохранив таблицы в прежней схеме. Node.js и файлы макета для сервера не нужны. `frontend-prototype/` — локальный справочный материал, исключённый из Git.

```bash
cp backend/.env.example backend/.env
cd backend
uv sync --locked
```

Заполните `backend/.env`:

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | SQLAlchemy URL вида `postgresql+psycopg://USER:PASSWORD@HOST:5432/NEW_DATABASE`; для Supabase можно использовать Session pooler с `?sslmode=require` |
| `DATABASE_SCHEMA` | схема PostgreSQL, по умолчанию `talenthub_v2`; используется API, миграциями и демоскриптами |
| `JWT_SECRET` | случайный секрет от 32 символов |
| `TRUSTED_ORIGINS` | по умолчанию `*` — разрешены все origins; для ограничения укажите адреса через запятую |

Старая история миграций заменена начальной миграцией `20261106_0001`. В PostgreSQL новая версия использует собственную схему `talenthub_v2` и собственную таблицу `alembic_version`. Старая схема, её таблицы и ревизия `20261105_0002` остаются без изменений. Миграции создают выбранную схему, если она отсутствует; пользователю БД нужны права на её создание. Новая схема должна быть пустой либо уже содержать совместимую версию TalentHub v2. **Не используйте `alembic stamp` для обхода проверки старой истории.** Старые `COOKIE_SECURE`, `FRONTEND_DIST_PATH`, `DEMO_*_PASSWORD` и `MOCK_DATA_PASSWORD` игнорируются.

API, миграции и сид устанавливают `search_path` на `DATABASE_SCHEMA` для каждого соединения. Прежняя схема `public` не добавляется в путь поиска, поэтому отсутствие таблицы в новой схеме не приводит к чтению старой таблицы. Изменять настройки роли PostgreSQL или дописывать схему в `DATABASE_URL` не требуется. Для SQLite настройка схемы не применяется.

## Запуск и демоданные

Из корня репозитория:

```bash
./dev.sh
```

Скрипт применяет миграции и запускает один процесс API на `http://127.0.0.1:8000`. Он не запускает сид и не очищает данные. В другом терминале подготовьте демонстрационные данные:

```bash
./seed_demo.sh
```

Сид добавляет отсутствующие записи со стабильными UUID. Повторный запуск сохраняет пароли, изменения профилей, даты, заявки, привязки и принятые решения. Даты новых демособытий считаются относительно дня подготовки набора в `Europe/Minsk`.

| Роль | Email | Пароль |
| --- | --- | --- |
| Ученик | `alina@demo.by` | `demo1234` |
| Родитель | `olga@demo.by` | `demo1234` |
| Модератор | `admin@demo.by` | `demo1234` |
| Ученик с незаполненным профилем | `mark@demo.by` | `demo1234` |

У Ольги сразу привязана и выбрана дочь **Алина Коваль, `2010-04-12`**. Повторный сид добавляет отсутствующую связь, сохраняя уже выбранного ребёнка. Явный сброс восстанавливает Алину как выбранную дочь. Школы и компании входят через `/auth/organization-login` по токену. Демо-токены для `school`, `company`, `school2` и `academy` определены в `backend/app/scripts/seed_demo.py` как `DEMO_ORGANIZATION_TOKENS`; повторный сид сохраняет уже выданные токены. Дополнительные представители: `school2@demo.by` и `academy@demo.by` (почта служит контактными данными). Они подходят для проверки второй школы и академии. Во вкладке компании «Запросы школ» сид сразу готовит два допущенных публичных запроса: наставники для хакатона от Лицея БГУ и практическая лаборатория от Гимназии №1 Минск. На оба можно отправить отклик.

Явный сброс демосценария выполняется только командой:

```bash
./reset_demo.sh --confirm-reset
```

Сброс удаляет демопользователей, мероприятия демоорганизаций, их партнёрские запросы и зависимые записи, включая созданные вручную заявки на эти мероприятия. Затем восстанавливает набор и его даты. Посторонние аккаунты и справочник организаций сохраняются. Используется БД из `DATABASE_URL`; перед запуском проверьте назначение. Обычный запуск и сид этой операции не выполняют.

Прежние команды `seed_mock.sh` и `reset_mock_data.sh --confirm-reset` перенаправлены на новый набор. `reset_mock_passwords.sh --confirm-reset` явно возвращает пароли только демоаккаунтов к `demo1234`.

## Контракт для фронтенда

- Префикс API: `/api/v1`.
- [Swagger UI](http://127.0.0.1:8000/docs), [OpenAPI JSON](http://127.0.0.1:8000/openapi.json), [health](http://127.0.0.1:8000/health) доступны в корне сервиса.
- Login/register возвращают `{access_token, token_type: "bearer", expires_in: 28800, user}`. Токен хранится фронтендом в `sessionStorage`, передаётся в `Authorization: Bearer <token>`. Восстановление — `GET /api/v1/auth/me`, выход — удаление токена из вкладки. Cookie-сессии не используются.
- Роли: `student`, `parent`, `school`, `company`, `moderator`. Компании и академии используют роль `company`; модератору соответствует экран `/admin`.
- Саморегистрация доступна только ученику и родителю. Роль и организация для операций читаются из текущей записи пользователя в БД.
- Списки возвращаются целиком в `{items: [...]}`. Даты — `YYYY-MM-DD`, временные отметки — UTC. Дедлайн действует включительно по календарному дню в `Europe/Minsk`.
- Ошибки имеют форму `{error: {code, message}}`. Коды HTTP: `401` вход/токен, `403` роль, `404` ресурс/видимость, `409` состояние/лимит/неоднозначность, `422` валидация. Схемы ответов и примеры пользователей всех ролей включены в OpenAPI.
- Каталог показывает только `published`. Повторяемый query-параметр `interest` объединяет направления через «ИЛИ». `application_status=none` означает отсутствие заявки, а `cancelled` — отменённую заявку. Персональный фильтр доступен только ученику.
- Для регистрации достаточно открытого события, действующего дедлайна и заполненного профиля. Диапазон классов — целевая аудитория. Вместимость проверяется при подтверждении, а не при подаче заявки.
- Родитель создаёт одну многоразовую ссылку через `GET/POST/DELETE /parents/me/invitation`. Авторизованный школьник присоединяется через `POST /family-invitations/accept` с `{token}`. Удаление ссылки не удаляет детей. Прежние `PUT /parents/me/child` и `POST /parents/me/children` закрыты.
- Модератор управляет аккаунтами школ и компаний через `GET/POST /moderation/organization-accounts`; `POST /moderation/organization-accounts/{id}/token` перевыпускает токен. Секрет возвращается только при выдаче. Перевыпуск отзывает старый токен и сессии аккаунта. Парольный вход организаций закрыт. Миграция `20261107_0004` заполняет недостающие токены только исходных активных демоаккаунтов, если им ещё ни разу не выдавался доступ; перевыпущенные токены сохраняются. Остальным существующим организациям нужно выдать токен в кабинете модератора; создание аккаунта заново не требуется.
- `/auth/organization-login` принимает `{token, expected_role}` и возвращает обычную восьмичасовую Bearer-сессию. Приглашения имеют отдельное назначение и не принимаются как токены авторизации.
- Посещение и подтверждённое достижение — отдельные записи. Отметка посещения не создаёт достижение. Новые внешние достижения, `deadline` и `invite` в этой версии создаёт сид.

Пример входа:

```bash
curl -X POST http://127.0.0.1:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"alina@demo.by","password":"demo1234","expected_role":"student"}'
```

| Экран | Группы API |
| --- | --- |
| Регистрация / вход | `/auth`, `/organizations`, `/reference-data` |
| Первый вход / профиль | `/students/me`, `/reference-data`, `/events?upcoming=true` |
| Каталог / рекомендации | `/events`, `/recommendations` |
| Заявки / успехи / уведомления | `/registrations/me`, `/students/me/success`, `/notifications/me` |
| Родитель | `/parents/me/children`, `/parents/me/invitation`, `/family-invitations/accept` |
| Школа / компания | `/organizations/me/dashboard`, `/organizations/me/events`, `/events/{id}/registrations` |
| Школьный реестр | `/organizations/me/students` |
| Партнёрства | `/partnership-requests`, `/partnership-responses` |
| Модератор | `/moderation/queue`, `/moderation/{тип}/{id}/decision`, `/moderation/organization-accounts` |

API не отдаёт HTML фронтенда или SPA fallback. Неизвестные пути возвращают `404`. CORS разрешает `Authorization`; по умолчанию доступны все origins (`TRUSTED_ORIGINS=*`). Интеграция с макетом и изменение его файлов не входят в бэкенд.

## Структура бэкенда

Модели, схемы, сервисы и роуты сгруппированы по предметным областям: `auth`, `students`, `events`, `registrations`, `partnerships` и другим. Общие компоненты слоя находятся в его подпакете `shared`.

```text
backend/
  app/
    models/<область>/          # ORM-модели; общий реестр — models/__init__.py
    schemas/<область>/         # запросы, ответы и краткие карточки
    services/<область>/        # правила, выборки и сборка ответов
    routes/<область>/router.py # HTTP-обработчики
    core/                     # настройки, безопасность, ошибки
    db/                       # Base, engine и сессии
    scripts/                  # явные команды подготовки и сброса данных
  tests/
    api/                      # HTTP-контракт, роли и сквозные сценарии
    integration/              # БД, миграции, сид, ограничения и конкуренция
    unit/                     # чистая логика без БД и HTTP-клиента
    support/                  # общие фикстуры
```

## Проверка

```bash
cd backend
uv run --locked pytest -q

# Отдельные наборы
uv run --locked pytest tests/api -q
uv run --locked pytest tests/integration -q
uv run --locked pytest tests/unit -q
```

API- и интеграционные тесты по умолчанию используют отдельный временный SQLite-файл, применяют миграцию и не читают `DATABASE_URL` как тестовую БД. Подготовка и сид БД подключаются через фикстуры этих двух наборов. Юнит-тесты запускаются без миграций, сида и HTTP-клиента. Покрыты пять входов, роли, профиль и смена школы, родительская привязка, модерация, каталог, рекомендации, заявки, лимит мест, посещение, уведомления, партнёрства, миграция, повторный сид и явный сброс.

Для проверки блокировок нужен PostgreSQL. Создайте отдельную тестовую БД с именем, начинающимся на `talenthub_test`, и укажите её явно:

```bash
TALENTHUB_TEST_DATABASE_URL='postgresql+psycopg://USER:PASSWORD@localhost:5432/talenthub_test' \
  uv run --locked pytest -q
```

Тесты PostgreSQL создают уникальную схему `test_<uuid>` и удаляют только её после завершения; подключению нужны права на создание схем. Чужое имя БД отклоняется до очистки данных. Тесты не вызывают `drop_all`. На SQLite пропускаются две проверки конкурентных операций и проверка изоляции схем: для них нужен PostgreSQL. Проверка изоляции создаёт две временные схемы в тестовой БД, подготавливает старую ревизию и записи, применяет новую миграцию и сид, затем проверяет сохранность старых данных.

## Развёртывание на Render

Создайте Python Web Service со следующими настройками:

| Настройка | Значение |
| --- | --- |
| Language / Runtime | `Python 3` |
| Root Directory | оставить пустым — корень репозитория |
| Build Command | `bash backend/render-build.sh` |
| Start Command | `bash backend/render-start.sh` |
| Health Check Path | `/health` |

В Environment задайте `DATABASE_URL`, `JWT_SECRET` и `TRUSTED_ORIGINS`. `DATABASE_URL` можно оставить прежним: новая версия автоматически создаст и будет использовать отдельную схему `talenthub_v2`, сохранив старую схему. Для другого имени задайте `DATABASE_SCHEMA` одинаково для сервиса и команд подготовки данных. Python 3.13 указан в корневом `.python-version`.

[`render-build.sh`](backend/render-build.sh) создаёт отдельное окружение `.render-tools`, устанавливает в него `uv==0.11.6` и вызывает этот бинарник напрямую для `sync --locked --no-dev`. Это обходит оболочку Render, которая может присутствовать в `PATH` без установленного `uv`, когда lockfile находится в подпапке. Зависимости приложения устанавливаются в `backend/.venv`; сборке не нужен доступ к БД.

Если в Render уже задан Root Directory `backend`, используйте команды `bash render-build.sh` и `bash render-start.sh`. Оба варианта поддерживаются: скрипты сами переходят в свою директорию.

[`render-start.sh`](backend/render-start.sh) проверяет обязательные переменные, применяет миграции и запускает Uvicorn одним процессом без `--reload`. Если миграция завершается ошибкой, сервер не запускается. Используется `0.0.0.0:$PORT`, с локальным запасным портом `10000`, согласно [требованиям Render к портам](https://render.com/docs/web-services#port-binding).

Скрипты не запускают сид и не сбрасывают данные. Для подготовки демонабора отдельно выполните в Render Shell из `backend`:

```bash
.venv/bin/python -m app.scripts.seed_demo
```

Фронтендеру передаются URL сервиса, `/docs`, `/openapi.json` и таблица демологинов; `TRUSTED_ORIGINS=*` разрешает запросы с любого домена. После деплоя проверьте `/health` и вход через `/docs`. Для отката кода выберите предыдущий успешный деплой в Render; это не откатывает миграции и данные БД. Само развёртывание из этой сессии не выполняется.

## Интеграция актуального фронтенда

Миграция `20261106_0002` добавляет существующие сценарии нового фронтенда, сохраняя данные схемы v2:

- `GET/POST /api/v1/parents/me/children` — несколько привязанных детей; `active_child_id` возвращается в GET.
- `PUT /api/v1/parents/me/children/{id}/select` — выбор активного ребёнка.
- `GET /api/v1/parents/me/children/{id}/recommendations` — рекомендации привязанному ребёнку с повторяемым `interest`.
- `GET /api/v1/parents/me/suggestions` и `POST /api/v1/parents/me/children/{id}/suggestions` с `{event_id}` — предложения ребёнку и уведомление `invite`.
- `PUT /api/v1/notifications/{id}/read` — идемпотентное прочтение собственного уведомления.
- `GET /api/v1/schools?q=` — школьный справочник с показателями только по подтверждённым достижениям и типу/интересам связанного мероприятия. Посещения не увеличивают эти показатели.
- `all_companies` — публичные предложения школ компаниям и академиям. `view=marketplace` и отклики теперь доступны обеим сторонам; в отклике `organization` содержит отвечающую организацию, `school` сохраняется для школ и равен null для компаний.
- Школьный реестр дополнен массивами `applications`, `attendances`, `achievements` для существующих карточек активности.

Сингулярные `/parents/me/child` сохранены и возвращают активного ребёнка. Создание связи не требует регистрации ребёнка заново. Ранее существовавшие привязки переносятся в список детей миграцией.

Фронтенд подготовлен в отдельном репозитории `talenthub-frontend/talenthub_frontend`, ветка `feat/backend-link-implementation`. Перед использованием новых методов нужно развернуть эту версию бэкенда; обычный start-скрипт применит миграцию. Деплой из текущей сессии не выполнялся.
